# Лабораторна робота 2: структурне тестування, модульні, інтеграційні та контрактні тести

## 1. Що виконано

У проєкті реалізовано окремий тестовий контур у папці `testing/`, щоб тестування не змішувалося з основним кодом у `src/`.

Додано:

- модульні (white box) тести для основної бізнес-логіки `jobsService`
- вузькі інтеграційні тести безпеки (JWT + data isolation)
- контрактні тести для 2 ключових бізнес-процесів

## 2. Структура тестового контуру

- `testing/jest.config.js` - ізольована конфігурація Jest
- `testing/tests/unit/jobsService.test.js` - модульні тести
- `testing/tests/integration/security.integration.test.js` - вузькі інтеграційні тести безпеки
- `testing/tests/contract/auth.contract.test.js` - контракт API видачі токена
- `testing/tests/contract/jobLifecycle.contract.test.js` - контракт API життєвого циклу задачі
- `testing/tests/helpers/` - тестові хелпери для app/db/auth

## 3. Контрактні бізнес-процеси

### Процес 1: Аутентифікація

Контракт тест перевіряє `POST /auth/token`:

- валідний формат відповіді: `accessToken`, `tokenType`, `userId`
- коректна валідація невалідного `userId`

### Процес 2: Життєвий цикл Job

Контракт тест перевіряє:

- `POST /jobs` -> статус `CREATED`
- `PATCH /jobs/:id/status` переходи `QUEUED -> PROCESSING -> DONE`
- валідність структури відповіді Job на кожному кроці
- узгодженість стану через `GET /jobs/:id`

## 5. Відповіді на контрольні питання

1) Що таке піраміда тестування і чому вона піраміда?

Піраміда тестування - це модель розподілу тестів за рівнями: в основі багато швидких unit-тестів, вище менше інтеграційних, на вершині найменше E2E/UI. Це "піраміда", бо кількість тестів зменшується вгору, а ціна/повільність росте.

2) Типи структурного покриття, порівняння.

- Line coverage: чи виконано рядки коду
- Statement coverage: чи виконано всі оператори
- Branch coverage: чи пройдено обидві гілки умов/перемикань
- Condition coverage: чи були булеві підумови і true, і false
- Path coverage: чи покриті шляхи виконання (зазвичай комбінаційно вибухає)

Branch і condition сильніші за line/statement для умовної логіки.

3) 100% statement і branch означає відсутність помилок?

Ні. Це лише показує, що код виконувався певними сценаріями. Можуть залишатись помилки в вимогах, побічних ефектах, конкурентності, інтеграції, асинхронності, некоректних асертах і неочевидних комбінаціях даних.

4) Як валідувати покриття? Приклади мутаційних тестів.

Валідувати покриття варто мутаційним тестуванням (Stryker): змінювати код штучними "мутаціями" і перевіряти, чи тести падають.

Приклади мутацій:
- `>` замінити на `>=`
- `&&` замінити на `||`
- повернення `true` на `false`
- прибрати виклик валідації
- замінити статус `DONE` на `ERROR`

Якщо тести не зловили мутацію - набір тестів слабкий.

5) Код має 100% line coverage. Який statement coverage?

Не обов'язково 100%. Часто близько до 100%, але один рядок може містити кілька операторів, і не всі оператори могли виконатись.

6) Що таке інтеграційні тести? Які типи?

Інтеграційні тести перевіряють взаємодію модулів між собою (роути + middleware + БД + зовнішні сервіси).

Типи:
- вузькі (narrow): частина ланцюга, часто з test doubles
- широкі (broad): майже весь стек, реальні залежності
- контрактні (provider/consumer contracts)

7) Недоліки широких інтеграційних тестів.

- повільні
- нестабільні (flaky)
- дорогі в підтримці
- складна діагностика причин падіння
- важко покрити багато edge-cases

8) Test doubles: dummies, mocks, fakes, stubs, spies.

- Dummy: передається, але не використовується
- Stub: повертає заготовлені значення
- Fake: спрощена робоча реалізація (наприклад, in-memory repo)
- Spy: записує факти викликів
- Mock: перевіряє очікувані взаємодії (скільки разів/з чим викликали)

9) Структура тесту. AAA, GWT.

AAA:
- Arrange: підготовка даних
- Act: виклик дії
- Assert: перевірка

GWT:
- Given (умови)
- When (подія)
- Then (очікування)

10) FIRST, right-BICEP.

FIRST:
- Fast
- Independent
- Repeatable
- Self-validating
- Timely

right-BICEP (вибір підходу до перевірки):
- Right: чи це правильний результат
- B: Boundary conditions
- I: Inverse relationships
- C: Cross-checks
- E: Error conditions
- P: Performance characteristics

## 6. Висновок

Основний функціонал backend покрито модульними тестами, безпекова складова перевірена вузькими інтеграційними тестами, а два ключових бізнес-процеси зафіксовані контрактними тестами в окремому тестовому контурі.
